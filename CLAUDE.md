# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

AI photo booth web app for the 2026 나주영산강축제 (Naju Yeongsan River Festival). Visitors pick a Yeongsan River scene, see themselves composited into it live, shoot, add a short handwritten-style message onto a printed-style frame, and take the result home via QR code. All UI text, error messages and code comments are in Korean — keep it that way.

## Commands

```bash
python3.12 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python scripts/fetch_models.py   # downloads RVM ONNX model + MediaPipe assets (once; gitignored)
python main.py                   # http://localhost:8080
YS_HTTPS=1 python main.py        # self-signed https on :8443 so phones on the same Wi-Fi can use the camera
docker build -t booth . && docker run -p 8080:8080 booth
```

There is no test suite, linter, or frontend build step. The frontend is plain ES modules served as-is from `web/`. To verify changes, run the server and hit endpoints (e.g. `curl localhost:8080/api/config`, or POST a JPEG to `/api/shots` with form fields `photo` and `bg`). Browser cameras only work on `localhost` or https.

Env vars (`PORT`, `YS_HTTPS`, `YS_PUBLIC_URL`, `YS_KEEP_HOURS`, `YS_MATTING_SIZE`, `YS_OUT_DIR`) are documented in README.md.

## Architecture

**Two-stage compositing.** The browser shows a *preview*. `web/live.js` (`LiveStage`) runs MediaPipe segmentation from a CDN: a multiclass model on desktop, a light selfie model on touch devices (where mask index 0 means *person*, the opposite of desktop). The capture sent to the server is the **raw camera frame**, not the preview. The server then re-composites at high quality in `booth/compose.py`: RVM matting via onnxruntime (CUDA when available and `YS_DEVICE` isn't `cpu`, else CPU; lazily loaded singleton, preloaded in the FastAPI lifespan; `YS_MATTING_MODEL` mobilenetv3 by default, resnet50 in the GPU build via `docker-compose.gpu.yml`) → `open_gaps` + `solidify` (`open_gaps` marks enclosed background regions larger than 0.4% of the body — the space between a V-sign hand and the face, the gap inside an arm on a hip — and those are never filled; `solidify` then fills only the small holes and speckled semi-transparency inside the body; on GPU with `YS_SEGMENT_MODEL=birefnet` the body core comes from BiRefNet lite and RVM only supplies hair detail, `_merge_body`) → blur-fusion foreground estimation (de-halo) → `decontaminate` (pulls leftover original-wall color out of semi-transparent edges) → LAB color harmonization toward the background → `match_texture` (sharpens the soft webcam person toward the background's detail level, gated above the noise floor). From there `compose()` returns **two images from one matting pass** (plus the person alpha as uint8, which `booth/ai.py` reuses so the AI step never mattes again):
- **`plain`:** the result + light wrap + vignette.
- **`shot` (scene filter):** `scene_match` (pulls the person's tone percentiles and highlight/shadow colors toward the background, plus the per-scene `look.tint`/`exposure`) → `beautify` (person-only skin smoothing, tone, vibrance, glow, detail restore) → `rim_light` (lights the person's edges facing `look.sun`) → light wrap → vignette.

Both images then get `occlude`: `backgrounds/fg_N.png` (optional grayscale mask of near objects such as reeds, flowers, fences, generated by `scripts/make_foreground.py` with Depth Anything V2 Small and checked by eye) re-draws those background pixels over the person so they stand *in* the scene. It is limited to below the upper part of the person so faces are never covered. The same layer is served as `/bg/{id}_fg.webp` and drawn on top in the live preview (`LiveStage.setBackground(img, fg)`); `/api/config` marks such backgrounds with `fg: true`. `YS_BEAUTY` scales the filter (0 disables). The background pixels are deliberately never filtered: users want the scenery crisp. Each `BACKGROUNDS` entry has a `look` dict. Its `sun` is in *original* image coordinates and is remapped through the cover crop. Its `preview` is a CSS filter that `LiveStage.setLook()` applies to the person layer in the desktop preview only (skipped on mobile for performance). If no person is detected, `compose()` returns the raw cropped photo with `person: False` and the flow continues. Do not turn this back into an error. Output is 1600×1200 (`SHOT_W/H`). Composition is CPU/memory heavy (~350MB per concurrent job). `main.py` gates it with an `asyncio.Semaphore(COMPOSE_SLOTS)` (`YS_COMPOSE_SLOTS`, default 2), and ORT `intra_op_num_threads` is cores/slots. Load-tested at 16 simultaneous shots with a peak of 1.2GB; without the gate it grows unbounded.

**Request flow** (`main.py`):
1. `GET /api/config`: backgrounds plus frame geometry. The frontend drives everything from this.
2. `POST /api/shots` (photo + bg id) → `output/{sid}_shot.jpg` (filtered) and `{sid}_plain.jpg`. The response includes the `look` name and `person`. The review screen toggles between the two.
3. `POST /api/shots/{sid}/final` (message, `filter` bool). If `filter` is false, plain is copied over shot first, so `shot.jpg` always holds the visitor's choice. `plain.jpg` is deleted once the final image is rendered. Then `booth/frame.py` pastes the shot into `frame/frame1.png` and renders the message → `{sid}_final.jpg`. The response includes the QR URL and the public page URL `/p/{sid}`.
4. `GET /p/{sid}/ai`: whether the optional AI version is ready (`off`/`pending`/`ready`/`failed`). It lives under `/p/` so `guard_public` lets the visitor's phone reach it.
5. `/p/{sid}` serves `web/photo.html` with `{{SID}}`/`{{STATE}}` string-substituted. This is the visitor's phone download page.

**Management page** (`/manage`, `web/manage.html`). Password-only (`YS_MANAGE_KEY`, default `ysg2026!`, empty env falls back to that default so there is never an empty password). Five wrong tries lock *that device* for an hour. `GET /manage` hands out a device cookie `ys_mdev` for this, because behind Docker Desktop every client arrives from the same IP, so an IP lock would lock out the operator too. Requests without the cookie (bots hitting the login API directly) share one bucket. The cookie `ys_manage` holds an HMAC of the key, not the key. It is deliberately *not* in `PUBLIC_PATHS`, so with `YS_OPEN=1` it is reachable from the internet and the password is the only lock. The page lists finalized shots newest-first (time, place, message, AI badge). Photos load only when '사진 보기' is clicked, and the QR dialog shows no photo, because bystanders may see the screen. Actions are QR + link copy and delete (files + record). **Group albums** (`booth/albums.py`, `OUT_DIR/albums.json`): for groups shot one person at a time, the operator ticks rows (Shift-click selects a range), optionally names the group, and gets one QR for `/p/album/{aid}` (public, under `/p/`). Photos are stored as ids only, sorted into finish order (records.jsonl order, since timestamps are whole seconds and can tie), capped at 60; expired photos drop out and `albums.prune()` (hourly, with `storage.cleanup`) removes empty albums. The album page grid is server-rendered (works without JS). Visitors open it on phones, so saving is per platform. On iPhone, '모두 저장' fetches every photo and calls `navigator.share({files})`, whose '이미지 n개 저장' puts them in Photos; it needs a second tap if the fetch outlasted the user activation. On Android, the system share sheet has no save-to-gallery target, so it does sequential `?download=1` downloads. Chrome asks once to allow multiple downloads, and the files land in the gallery's Download album. A web page cannot write into the Android camera album: Samsung Gallery shows these under 앨범 → 다운로드, and Google Photos only under 라이브러리 → 기기의 사진 → Download, so users thought saving had failed (user report, 2026-10-08; server logs showed the `?download=1` requests succeeding). After an Android save, both pages show and scroll to `#savedGuide`, which says exactly where the photo went. Download filenames include `sid[:6]` so a batch doesn't get '(1)', '(2)'. The single-photo page uses the same Android rule. The ZIP (`/p/album/{aid}/photos.zip`, built once per album into `OUT_DIR/albums/{aid}_{count}.zip` and reused) is only linked on computers, because a ZIP is hard to save on a phone (user feedback). Tapping a photo opens its own `/p/{sid}` page (versions, AI effects). There is no mail or SMS resend, and visitor names and contacts are never collected. The header chips also show live load: busy compose slots, the AI queue depth and today's GPT usage and cost.

**Records** (`booth/records.py`): `OUT_DIR/records.jsonl`, one JSON line per finalized shot (`id`, `t`, `bg`, `place`, `name`, `msg`, `filter`). No database, so copying the folder moves everything. `note_shot()` remembers the chosen background at `/api/shots` (in-memory, capped) and `add()` writes the line at `/final`. `storage.cleanup()` prunes records alongside expired photos.

**Concurrency.** Shooting is gated by `asyncio.Semaphore(COMPOSE_SLOTS)`; `_busy` counts photos composing or queued, and the manage page shows it. The AI queue is separate and always yields to shooting: `_wait_for_idle()` holds AI work back while every compose slot is taken, jobs older than `YS_AI_TTL` (180s) are dropped because the visitor already left, and an overflowing queue (`YS_AI_QUEUE`, 8) drops the new job. No path through the AI feature can make a visitor wait.

**One-cut and four-cut (인생네컷).** The mode switch lives on the places screen. In 4-cut mode the visitor banks four places (`state.picks`, with a random-fill button), confirms a guide dialog (`#cutGuide`), then shoots **one cut per shutter press**: each press runs the timer countdown, captures, uploads without awaiting (`state.jobs`), switches to the next place and returns with the badge in a pulsing 'waiting' state until the visitor presses again. (It used to auto-advance every 3s; festival feedback was that there was no time to pose.) Compositing overlaps the shooting; after the fourth press the busy overlay counts finished cuts until `Promise.all(state.jobs)` resolves, and any failed cut restarts the set from cut 1. Note: in headless Chrome with a fake camera, `live.capture()` alone can take 7s+ (software WebGL), so browser tests need generous timeouts. The review and write screens use a client-side 2×2 canvas built by `makeGrid()`, which mirrors `frame.grid()` exactly (1600×1200, 10px gap, #f4fcff). `POST /api/shots/{sid}/final` takes `cuts: [id, id, id]`; the server renders all four into `frame.render()` and writes the frameless 2×2 over the lead's `shot.jpg`, then deletes the other cuts' files. **No new frame art was needed:** `FRAME_HOLE` is 877×661, so a 2×2 split with `FRAME_GAP` leaves each cell at exactly 4:3 — `frame.cells(n)` returns one box for 1 cut and four for 4. Finalize is idempotent (it no-ops when `final` already exists), so a double tap cannot duplicate a record or re-render over the merged grid. For AI, each cut is relit separately (different backgrounds); `ai.note_final(sid, msg, cuts)` records the group, `_finish_ready()` fires on every completion and only assembles once all members are ready, and `status()` reports `pending` for a group until `aifinal` exists. Measured on the 3080 Ti: ~4.3s per cut warm, ~19s for a full four-cut set.

**VRAM (measured, critical).** The booth, IC-Light and the Windows desktop share one 12GB card. Left alone, onnxruntime's CUDA EP grabbed **~9.3GB at startup** (cuDNN max workspace + an arena that only grows), IC-Light held ~2.3GB, and the card sat at ~12GB. Windows then pages GPU memory to system RAM: shots took 37–90s and the whole PC froze. Fixes, all in `compose.py`: `cudnn_conv_use_max_workspace=0`, `arena_extend_strategy=kSameAsRequested`, the run option `memory.enable_memory_arena_shrinkage=gpu:0` on every `sess.run` (returns memory after each inference), and `_gpu_lock` so only one GPU inference runs at a time (CPU post-processing stays parallel; on CPU nothing is locked). IC-Light calls `torch.cuda.empty_cache()` after each job. Result: ~3.5–4.4GB steady, ~8.3GB transient peak with six simultaneous shots, 0.7–0.8s per shot. **Do not set a hard `gpu_mem_limit`** (`YS_GPU_MEM_MB`): BiRefNet at 1024×1024 needs several GB briefly, and even a 5GB cap made the booth fail at warmup, which takes the whole site down. If VRAM creeps up again, check with `docker exec yeongsangang-ic-light-1 nvidia-smi` (Windows-side apps were only ~0.36GB here).

**GPU contention (measured, important).** On this Windows/WSL2 box, two processes using the GPU at once slow each other dramatically: while IC-Light runs, the booth's matting goes from ~0.65s to 17–21s per shot, and shrinking the IC-Light job does not help. So the local AI never overlaps shooting: `ai.note_activity()` is called on every `/api/shots`, the worker waits for `YS_AI_IDLE` (6s) of quiet (`_wait_quiet`), and only around the IC-Light HTTP call (`_relight`) does it hold *every* compose slot (`_take_gpu`/`_free_gpu`), re-checking for new activity after acquiring. `_prepare` and `_finish` are CPU-only and run outside the lock. External engines skip all of this. The server logs `[촬영] 받기 · 합성 · 저장` timings per shot so a slowdown at the venue is visible immediately.

**AI effect buttons (GPT, optional, paid)** (`booth/effects.py`). With `YS_OPENAI_KEY` set, the phone page shows buttons for `config.EFFECTS` (AI 장면 연출 / 수채화 / 웹툰 / 필름). Unlike the light pass, these change the picture itself, so results are used as-is (faces may drift; the original always stays). Generation is on demand only, from `POST /p/{sid}/fx/{fx}` (under `/p/` so it is public), once per photo and effect (file existence is the cache), bounded by a daily cap (`YS_GPT_DAILY`, counts edits, a four-cut set is 4) and `YS_GPT_PARALLEL` concurrent calls. It calls `POST /v1/images/edits` (multipart, `gpt-image-2`, 1024×768 which is 4:3, `output_format=jpeg`) with stdlib urllib. For four-cut, finalize keeps each cut as `{lead}_c0..c3.jpg` so effects run per cut and are re-assembled with `frame.save_grid`/`frame.render`, which accept PIL images as well as paths. Files are `fx_{id}` (frameless) and `fxf_{id}` (framed). The booth only shows an overlay on the take screen (`#fxOverlay`); the phone asks for consent the first time before sending a photo out. Cost at medium quality is about $0.07 per edit. Without a key, `catalog()` is empty and nothing shows.

**Frame geometry has to match on both sides.** `FRAME_HOLE`, `FRAME_TEXT_BOX`, `TEXT_COLOR` and `DEFAULT_MESSAGE` in `booth/config.py` are pixel coordinates on the 1024×1536 `frame1.png`. They are sent to the client via `/api/config`. `fitMessage()` in `web/app.js` mirrors `frame.layout_message()` so the preview matches the output: up to 3 visitor-typed lines, each auto-wrapped to the box width (`_wrap`/`wrapLine`: break at spaces, by character if one word is wider than the box), the largest size from 72px down to 22px in steps of 2 whose wrapped line count fits the box height at line height 1.25, then `_balance`/`balanceLine` narrows the width by binary search, keeping the line count, so lines come out even. (Before wrapping, a long single line shrank to ~22px and could overflow the box.) Verified identical sizes and breaks for 9 sample messages in headless Chrome vs PIL. If you change one, change the other.

**Message fonts.** `config.FONTS` lists 9 handwriting styles (first = default `basic`, the Ownglyph font in the repo; the other 8 are Google Fonts OFL TTFs that `scripts/fetch_models.py` downloads at image build into the gitignored `font/extra/`; `config.fonts()` only lists files that exist, so a failed download just hides that option). Credits: `font/CREDITS.md`. `fonttools` is installed by its own `RUN` in the Dockerfile, deliberately *not* in requirements.txt, because touching requirements.txt re-runs the heavy pip layer and re-downloads an unpinned onnxruntime-gpu. The write screen shows each option as `/font/{id}.png` (the name rendered in that font, used as a CSS mask so it takes the button colour) and downloads `/font/{id}.ttf` only when picked (`FontFace`, family `ys-{id}`). Glyph fallback is the same on both sides: chosen font → Ownglyph → (server: NanumGothic; browser: system font). The server checks each character against the font's cmap (`frame._cmap`, fonttools) and draws mixed runs on one baseline (`_runs`/`_measurer`); characters no font has (emoji) are dropped rather than printed as boxes. The choice travels as `font` in `POST /final`, is stored in records.jsonl, and is reused by the AI light version (`ai.note_final`) and GPT effects (`effects._save`). Verified 27/27 identical layouts (9 fonts × 3 messages, including ♥ fallback) in headless Chrome vs PIL. The frame size `[1024, 1536]` is hard-coded in `main.py`.

**Backgrounds.** Files are `backgrounds/bg_N.png`, and each needs an entry in `config.BACKGROUNDS` (`id`, `name`, `place`, `story`). The id is used in URLs and filenames. The server never serves the PNGs directly: `/bg/{id}.jpg?w=` snaps the width to 480/800/1600 and returns an LRU-cached JPEG.

**Storage** (`booth/storage.py`): flat files in `OUT_DIR` named `{sid}_{kind}.jpg` (`shot|plain|final|ai|aifinal|c0..c3|fx_*|fxf_*`), plus `records.jsonl`. `remove(sid)` deletes every kind for one id (used by the manage page). The server generates ids with `secrets.token_urlsafe`, and they are regex-validated before building any path, which is the path-traversal guard. An hourly background task deletes files older than `KEEP_HOURS`.

**Internet exposure.** The `guard_public` middleware in `main.py` returns 404 for anything outside `PUBLIC_PATHS` (`/p/`, `/media/`, `/static/`, `/font/`) when a request comes from the internet. It detects that by the `CF-Connecting-IP` header (Cloudflare Tunnel) or by the host matching `YS_PUBLIC_URL`. Booth APIs then need the `ys_booth` cookie, which is set by opening `/?key=$YS_BOOTH_KEY` once (Plan A). Without the cookie they only work from localhost or a non-public LAN host. `YS_OPEN=1` disables the guard entirely (the home server currently runs open). If you add a file the visitor's photo page needs, add its prefix there. `docker-compose.yml` supports two deployments:
- **Plan A:** home PC + `.env`, either `cloudflared` via `--profile online` (A-1) or router port-forwarding + Caddy via `--profile web` (A-2, `Caddyfile`, `YS_DOMAIN`; Caddy passes the Host header through, which is what `guard_public` relies on). The current home PC (Windows + WSL2, RTX 3080 Ti) uses A-2 with `ysg26.cloud`.
- **Plan B:** offline venue laptop + router via `--env-file .env.local`. Inside Docker the LAN IP can't be auto-detected, so `YS_PUBLIC_URL` must be set.

`scripts/fetch_models.py` (run at image build) vendors MediaPipe into `web/vendor/mediapipe/` (gitignored). `live.js` prefers that copy over the CDN, so the live preview works offline. Keep `MP_VERSION` in sync between the two files.

**Laptop booth (current operating model, 2026-10-05).** Visitors are shot on a Windows laptop (no GPU) and download with their own mobile data. Normal mode: the laptop just runs Chrome in kiosk mode against the home server (`scripts/laptop/open-booth.bat` → `chrome-kiosk.bat`, which uses a dedicated `--user-data-dir` so `--kiosk` works even if Chrome is already open and the camera permission persists). Fallback when the home server is down: `docker-compose.laptop.yml` (project `yeongsangang-laptop`, CPU image `yeongsangang-booth:cpu`, photos in `output-laptop/`) runs the booth plus `cloudflared` as an account-less quick tunnel. The tunnel's URL is random per start; `main._watch_tunnel()` polls `YS_TUNNEL_METRICS` + `/quicktunnel` every 15s and stores it in `config.TUNNEL_URL`, which `public_base_url()` prefers after `YS_PUBLIC_URL`. Tunnel requests carry `cf-connecting-ip`, so `guard_public` exposes only `PUBLIC_PATHS` (YS_OPEN stays unset there); the booth itself is bound to 127.0.0.1. `/api/config` returns `public`, which `start-fallback.bat` polls before opening the kiosk. Verified end to end: QR pages, media and AI status are 200 over the tunnel, while `/`, `/manage`, `/api/config` and `POST /api/shots` are 404; CPU compose ~1.8s on the desktop CPU. The .bat files must keep CRLF (`.gitattributes`). Runbook: `docs/laptop-booth.md`.

**Public URL for QR codes.** `config.public_base_url()` checks `YS_PUBLIC_URL`, then the fallback quick tunnel (`TUNNEL_URL`), then `RENDER_EXTERNAL_URL` (Render), then `SPACE_HOST` (HF Spaces). Otherwise `main.base_url()` swaps a localhost host for the machine's LAN IP so phones can reach the booth laptop.

**Laptop UX (the booth runs on a Windows laptop).** `onKey()` routes keys per screen so the whole flow works from a keyboard or a presentation clicker: Enter/Space/PageDown = next/confirm, PageUp/Backspace = back, arrows = change place; in the message textarea only Ctrl+Enter or PageDown finish. Enter/Space on a focused button or `.deck-item` is left to the element so actions never fire twice. `FINE_POINTER` devices default the timer to 5s (time to step back from a laptop). The countdown keyframes start at opacity 1 (they used to fade in from 0, which made digits invisible when a slow laptop dropped frames), and `#lookUp` ("↑ 카메라를 봐 주세요") shows in the last second because the webcam sits above the screen. `live.js` measures each segmentation (`adapt()`), stretches `segEvery` to keep segmentation under ~40% of frame time, and swaps to the light selfie model after sustained >45ms (`swapLite()`); `loadSegmenter(kind)` sets the model and its mask semantics together. A `max-height: 820px` landscape breakpoint shrinks the topbar and folds the scene caption into one line (stage 845×634 at 1366×768). Also: Screen Wake Lock (`keepAwake`), cursor auto-hide after 3s, autofocus of the message box on fine pointers. Verified with puppeteer + a fake camera at 1366×768, 1536×864, 1280×720 and 1920×1080 (no overflow anywhere) and a remote-keys-only end-to-end run.

**Background music** (`web/music.js`, `createMusic(#music, #bgm)`). An ambient playlist of four CC BY 4.0 tracks by Kevin MacLeod (`bgm/carefree|life-of-riley|fretless|sunshine.mp3`, re-encoded to 128kbps, credits in `bgm/CREDITS.md` and the `.intro-credit` line, which the license requires) plays across every screen starting from a random track; `countdown()` ducks it for the beeps and shutter; `enterTake()` crossfades to the finale track `bgm/bgm1.mp3` (provenance unknown, ask the user before relying on it) and `goHome()` crossfades back. Mute is shared by the bottom-left `#musicBtn`, the take screen's `#muteBtn` and the M key, and persists in localStorage. Autoplay works in the kiosk Chrome (`--autoplay-policy=no-user-gesture-required`); elsewhere it starts on the first pointer or key event. Note: the Alpine headless Chromium used for tests cannot decode MP3 at all (even `bgm1.mp3`), so tests substitute WAV via request interception.

**Frontend** (`web/app.js`): one page with `<section data-screen=...>` screens toggled by `show()`: intro → places → studio → write → take. A topbar step indicator maps screens to steps. Kiosk behaviour matters: an idle timeout returns to intro, BGM is unlocked on the start tap (iOS autoplay rules), the camera auto-restarts when lost, a watchdog catches stalled video, and Space/Enter shoots (for a remote). Client errors go to the server log through `navigator.sendBeacon('/api/log')`. Many choices in `live.js` are iOS Safari workarounds (no OffscreenCanvas, a hidden-but-attached `<video>`). Read the comments there before changing them.

## Deployment notes

- The Dockerfile runs `scripts/fetch_models.py` at build time and installs `fonts-nanum`. `frame.py` falls back to NanumGothic when `font/OwnglyphPDH.ttf` is missing.
- `certs/` (self-signed cert, regenerated when the LAN IP changes, tracked via `certs/ip.txt`), `output/` and `model/*.onnx` are gitignored.
- `services/ic-light/` builds separately (PyTorch CUDA base, ~8GB image) and is only pulled in by `docker-compose.ai.yml`. It downloads SD1.5 + the IC-Light fbc weights (~6GB) into the `ai_cache` volume on first start, so its `/health` stays 503 for a few minutes.

**Optional generative-AI relighting** (`booth/ai.py`). After `/api/shots` has already answered, the shot is pushed onto a bounded `asyncio.Queue` (`YS_AI_QUEUE`, default 3; a full queue drops the job) and one worker makes an extra "AI version" in a thread. Nothing in the shooting/QR flow ever waits on it. The engine is picked from the environment by `detect()` (`YS_AI=auto`): a reachable local IC-Light service (`YS_AI_URL`, `services/ic-light`, GPU container from `docker-compose.ai.yml`) → an external image-edit API key (`YS_AI_KEY`, Gemini) → off. `_watch()` re-probes every 30s because the IC-Light container needs minutes to load its models, so it attaches by itself once ready; offline Plan B simply stays off.

The AI output is used **as light only**: `apply_light()` takes the per-pixel ratio between the AI result and the plain composite, multiplies it onto the person (alpha-weighted), and lets the background keep only the darkening part near the person (a cast shadow), after dividing out the AI's global background drift. So the face, its detail, and the crisp scenery are the originals — a generative model can never alter them. The result is `{sid}_ai.jpg` (plain composite + AI light + person-only `beautify`); `note_final()` renders it into the frame with the same message as `{sid}_aifinal.jpg`. `web/photo.html` polls the status endpoint for ~2 min and reveals a 기본 / AI 빛 보정 toggle when it lands. `/api/config` carries `ai: {on, external}`; `external` is true for the API engine, and the booth intro then shows a notice that photos leave the machine.
